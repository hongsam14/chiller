먼저, 이 문서의 결론

전체 컴플라이언스 점검 중 injection 및 페이로드 기반 능동 공격은 AI-Active-Scanner가, CVE PoC 점검은 Nuclei가 각각 담당합니다. 남는 영역 — 보안 헤더·쿠키·정보 노출·TLS 같은 위생·설정 항목(KISA 26개) — 은 “공격”이 아니라 “관찰”로 판정되므로, 이를 담당할 별도의 passive-scanner 엔진을 신규 구축합니다. 이 엔진은 ZAP passive + 단일목적 프로브 5종 + 엔진 네이티브 시그니처 6종으로 구성됩니다.

01
배경

컴플라이언스 커버리지와 passive-scanner의 필요성

목표는 KISA 기준 26개 점검 항목 전체에 대한 컴플라이언스 커버리지 확보입니다. 현재 이 커버리지에는 구조적인 공백이 있습니다.

기존 커버리지의 공백. 운영 중인 스캐너로는 injection 및 페이로드 기반 능동 공격(SQLi · RCE · SSTI · SSRF · XXE 등)을 담당하는 AI-Active-Scanner와, 알려진 취약점의 CVE PoC를 점검하는 Nuclei가 있습니다. 그러나 26개 항목의 상당수 — 보안 헤더, 쿠키 속성, 서버·프레임워크 버전 노출, 정보 누출, TLS 설정 — 은 공격이 아니라 응답 관찰과 설정 확인으로 판정되는 항목이라, 능동 공격·PoC 스캐너 어느 쪽으로도 구조적으로 커버되지 않습니다. 이 공백이 컴플라이언스 미충족으로 직결됩니다.

그래서 passive-scanner가 필요합니다. 위생·설정 항목을 관찰 기반으로 판정하는 전용 passive-scanner 엔진을 AI-Active-Scanner와 분리해 구축합니다. 크롤러로 상대 자산의 URL 목록을 이미 전수 확보했습니다(응답 본문은 저장하지 않음). 따라서 이 엔진은 “자산 발견”이 아니라 확보된 target URL을 스캔 시점에 다시 요청해 응답을 점검하는 데 집중합니다 — 크롤링·discovery가 불필요해 범위가 단순해집니다.

다른 스캐너와의 역할 구분. CVE PoC 점검은 Nuclei가 별도로 담당합니다 — 다만 Nuclei는 이 26개 컴플라이언스 항목에 대해서는 버전·시그니처 조각 매칭 오탐이 과다해 부적합하므로, 해당 역할은 passive-scanner가 맡습니다. 또한 ZAP의 active 전면 스캔은 AI-Active-Scanner의 injection 점검과 범위가 중복되어 오탐·트래픽만 늘리므로, ZAP는 passive 기능만 사용합니다.

02
설계 원칙

passive-scanner 엔진의 3개 구성

신규 엔진은 서로 다른 점검 방식 3개를 조율합니다. 방식이 다르므로 오탐이 구성요소별로 격리되고, 한 항목이 두 곳에서 중복 판정되지 않습니다. 기존 시스템(AI-Active-Scanner · Nuclei · ASM)은 이 엔진과 동시에 실행되지 않는 별도 단계로, 서로 다른 점검 영역을 담당합니다.

별도 · 기존

AI-Active-Scanner 기존

injection 및 페이로드 기반 능동 공격 — SQLi · RCE · SSTI · SSRF · XXE 등. 별도 단계로 동작하며 이번 구축 범위 밖.

별도 · 기존

Nuclei 기존

알려진 취약점의 CVE PoC 점검. 이 역시 별도 단계로 동작하며 이번 구축 범위 밖.

별도 · 기존

ASM 기존

공격 표면 관리(Attack Surface Management). HTTP Method 점검(PS-014)을 이미 제공하므로, 해당 항목은 신규 엔진 범위에서 제외.

구성 A

ZAP passive 연동 신규 엔진

확보된 URL 목록을 GET으로 다시 요청하고 응답을 관찰만 해서 판정(spider 없음, 공격 페이로드 없음). 위생 항목의 오탐을 구조적으로 억제.

구성 B

단일 목적 능동 프로브 신규 엔진

testssl.sh · Corsy · dirhunt · changeme · subzy를 어댑터로 연동. 각자 한 항목만 정밀 프로빙. injection 페이로드가 아니라 AI-Active-Scanner와 무충돌.

구성 C

엔진 네이티브 시그니처 신규 구현

전용 툴이 없거나 불필요한 6개 항목을 passive-scanner 엔진에 직접 구현. 확보된 URL을 다시 요청해 응답에 시그니처를 적용, 공격 페이로드 없는 benign GET으로 판정.

엔진 네이티브 기능 · 신규 구현

passive-scanner 엔진에 추가할 6개 점검

아래 6개는 전용 OSS에 의존하지 않고 passive-scanner 엔진에 네이티브 기능으로 직접 구현합니다. 크롤링이 이미 끝나 경로 discovery가 불필요하고(URL은 확보됨), 시그니처가 단순해 해당 URL을 다시 요청해 판정하는 편이 전용 툴보다 안정적이기 때문입니다.

PS-008

robots.txt 민감경로

robots.txt를 다시 요청해 민감 경로 패턴 매칭.

PS-011

.env 파일 노출

해당 경로를 요청해 body의 DB_PASSWORD=, APP_KEY= 앵커 검사.

PS-012

백업 파일 노출

확보된 .bak/.zip/.old 경로를 요청해 유효성 판정.

PS-013

관리자 페이지 노출

크롤러가 찾은 admin URL을 요청해 공개 접근 가능 여부 확정.

PS-022

crossdomain.xml 과도 허용

crossdomain.xml을 요청해 domain="*" 와일드카드 검사.

PS-023

CAPTCHA 부재

로그인 폼을 요청해 reCAPTCHA script/iframe 유무 판정.

이 6개는 Nuclei 커스텀 template으로도 구현 가능합니다. 이미 CVE PoC용으로 Nuclei를 운영 중이므로, 엔진 네이티브 구현 대신 전용 template을 추가하는 방식도 선택지입니다 — 단, 앞서 짚은 오탐을 피하려면 응답 body 앵커를 타이트하게 잡아야 합니다.

26개 항목의 처리 방식

관찰 14 — ZAP passive 연동

OSS 6종 연동으로 19개(관찰 14 + 프로브 5)를 커버하고, 6개는 확보된 URL을 다시 요청해 응답을 판정하는 엔진 네이티브 기능으로 구현합니다. 남는 PS-014(불필요한 HTTP Method)는 기존 ASM이 이미 점검하므로 신규 엔진 범위에서 제외합니다. injection 및 페이로드 기반 능동 공격은 AI-Active-Scanner가, CVE PoC 점검은 Nuclei가 각각 별도 단계로 담당하므로, 이 26개 컴플라이언스 항목과 겹치지 않습니다.

공통 사각지대인 PS-002 TLS 심층과 PS-025 Subdomain Takeover는 passive-ZAP도 일반 active 스캐너도 제대로 다루지 못하는 영역이라, 어떤 구성에서든 testssl.sh · subzy로 별도 유지됩니다.
06
실행

엔진 구축 단계

도구 7종은 입력(URL·도메인·로그인 폼)과 출력(JSON·텍스트) 포맷이 제각각입니다. 이를 KISA 항목으로 정규화하는 허브 역할은 passive-scanner 엔진 자체가 맡으며, 네이티브 점검 결과까지 하나로 병합합니다. 응답을 저장하지 않으므로, 엔진은 각 URL을 한 번만 요청해 그 응답을 ZAP passive 분석과 네이티브 시그니처 양쪽에 함께 태워 중복 요청을 피합니다.

ZAP passive 연동 구성

Automation Framework에서 spider 잡 제외 · 확보된 URL 목록을 GET으로 주입 · passive만 실행하도록 엔진에 통합.

프로브 5종 어댑터 개발

testssl.sh · Corsy · dirhunt · changeme · subzy의 target 입력·결과 파싱을 엔진 어댑터로 표준화.

엔진 네이티브 시그니처 6종 구현

PS-008 / 011 / 012 / 013 / 022 / 023 판정 로직을 엔진에 직접 구현 (크롤러 응답 재활용).

결과 정규화 스키마 정의

모든 구성의 출력을 PS-ID·심각도·증거(evidence)로 통일해 단일 컴플라이언스 리포트로 병합.
